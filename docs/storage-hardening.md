# 원고 저장과 복구

## 저장 구조

Firestore는 `users/{uid}/projects/{projectId}` 아래에 회차, 리비전, 장면, 인물, 세계관, 복선, 연표, 인물 관계, 집필 계획, Prompt Profile, Style Profile과 변경 제안을 별도 문서로 저장합니다. 회차는 최신 원고를, 리비전은 생성 당시의 원고를 보관합니다. 집필 실행 결과는 기존 개별 집필 흐름과 ProjectBundle을 사용합니다. 전체 백업의 ProjectBundle은 JSON 교환 구조입니다.

RAG 자료는 별도 MemoryDocument, MemoryChunk, 인덱스 매니페스트와 세대별 스테이징을 사용합니다. 서사 그래프와 지식 승인 기록은 별도 서버 관리 컬렉션에 저장됩니다. 정사 승인, RAG 출처 검증, 모델·차원, 활성 세대 및 재시도 경로는 기존 보호 조건을 사용합니다.

## 회차·Revision 크기 검사

회차 생성, 직접 업데이트, Revision 생성, CAS 및 ProjectBundle 가져오기의 회차·Revision preflight는 실제 저장 필드로 크기를 추정합니다. CAS 업데이트는 트랜잭션에서 읽은 기존 문서와 변경 필드를 함께 계산합니다. 한글과 이모지의 UTF-8 바이트, 필드명, 문서 경로, 배열·맵, Timestamp, Bytes, 참조, 벡터 등을 반영합니다. 지원하지 않는 타입은 저장 전에 오류를 표시합니다. 700 KiB부터 경고하고 900 KiB부터 차단합니다. 기존 원고와 복구본은 보존합니다.

Firestore 문서당 공식 최대치는 1 MiB입니다. NOVEL FORGE의 임계값은 내부 안전 여유이며 보안 규칙의 문자열 제한, 인덱스 엔트리와 Commit 요청 크기에 관한 제한은 별도로 적용됩니다. 서버의 원고 추출·정사 승인·RAG API는 기존 회차 및 Revision을 읽고 각자의 컬렉션에 씁니다. 이 크기 가드는 회차·Revision Client SDK 쓰기에 적용됩니다. ## 자동 저장과 복구

- 입력 직후 복구본을 IndexedDB에 기록합니다. 복구본 키는 UID·작품·회차·편집 세션을 포함하며, 동일 회차의 두 편집 세션은 각각 사본을 유지합니다. 각 사본에는 원고·제목·요약·작가 메모·관계와 CAS 기준, 저장 순서가 포함됩니다.
- 브라우저 트랜잭션 완료 뒤 로컬 보존 상태를 표시합니다. 실패하면 편집 중인 내용이 메모리에만 남을 수 있음을 표시합니다. 보호되지 않은 입력이 있으면 브라우저 종료 확인을 요청합니다. 종료 환경에 따라 브라우저가 확인을 표시하지 않을 수 있습니다.
- 입력이 멈추면 1,750 ms 뒤, 입력이 계속되면 20초마다 저장 기회를 엽니다. 같은 범위의 진행 중 요청이 있으면 최신 대기 사본 한 개를 유지합니다. 수동 스냅샷·복원·AI 반영도 같은 직렬 실행 경로를 사용합니다.
- 저장 Payload 해시는 본문 외에 회차 번호, 제목, 요약, 메모, 상태와 관련 ID 배열을 포함합니다. 본문 해시와 RAG 출처 해시의 의미는 유지합니다. 일반 자동 저장이 이미 원격에 반영된 경우 CAS 읽기로 동일 결과를 확인하고 문서 쓰기와 색인 요청을 생략합니다. 수동 스냅샷은 별도의 작가 의도이며 영구 Operation Receipt는 추후 범위입니다.
- 원격 오류 중 일시적인 네트워크 오류만 최대 3회 시도합니다. 로그인·권한·크기 제한·CAS 충돌은 자동 반복 없이 복구본을 유지합니다. 네트워크가 돌아오면 현재 편집 세션의 네트워크 대기 항목을 다시 검증합니다. 재시작 후 발견한 복구본은 작가가 선택합니다.
- 성공 응답이 복구본을 정리할 때 기록된 순서와 정확히 일치하는 항목만 제거합니다. 늦은 응답은 새 초안이나 다른 계정의 표시 상태에 적용되지 않습니다. 원격 기준이 바뀌었으면 충돌을 표시하고 복구본 JSON을 내려받아 비교할 수 있습니다.
- 로컬 작품 캐시는 UID별 키에 쓰고, 이전 캐시는 소유자가 일치하는 작품에 한해 읽습니다. 로그인 상태가 바뀌면 이전 요청의 응답을 화면에서 제외합니다. UID를 기록하지 않던 레거시 EmergencyDraftBackup은 원래 키에 보존합니다. 그 자료는 소유권 근거가 없어 자동 공개나 이관 대상으로 사용하지 않습니다.
- 로컬 작품의 브라우저 간 탭 경합에서는 Web Locks를 지원하는 경우 같은 UID의 CAS Commit을 직렬화합니다. 클라우드는 Firestore 트랜잭션과 콘텐츠·메타데이터 CAS를 사용합니다.

## 조회·색인과 대량 작업

로그인과 승인 작업 화면에서 중복된 변경 제안 컬렉션 조회를 제거했습니다. 기존 작품 상세 조회는 모든 회차·Revision을 읽습니다. 전체 데이터를 쓰는 Writer·검색·내보내기 입력과 분리된 초기 부분 조회가 남아 있습니다. 가져오기에서는 회차 및 Revision 크기를 첫 원격 쓰기 전에 검사합니다. 기존 ProjectBundle 저장은 개별 원격 작업을 순차 실행하므로 실패 시 앞선 쓰기가 이미 확정됐을 수 있습니다. 영구 체크포인트와 충돌 없는 대량 재개는 별도 검증이 필요합니다.

동일한 자동 저장은 색인 요청도 만들지 않습니다. 실제 변경은 기존 CANON 출처와 Revision 검증을 거치며, 기존 RAG의 유효 세대 검사와 실패 재시도를 계속 사용합니다. 색인 실패를 원고 텍스트 일치만으로 성공 처리하지 않습니다.

## 합성 벤치마크와 검증 범위

| 실험 | 환경 | 확인 결과 |
| --- | --- | --- |
| 입력 1,000회, 150 ms 간격 | 제어된 타이머와 CAS 저장 어댑터 | 회차 쓰기 8회, Revision 0개, 최대 저장 사이 간격 20.1초, 최종 원고 일치 |
| 동일 저장 100회 | CAS 저장 어댑터 직접 호출 | Snapshot 읽기 100회, 회차 쓰기 및 Revision 생성 0회 |
| 100 / 300 / 500화 | 실제 Auth·Firestore Emulator와 전체 작품 상세 저장소 | 각 4개 SDK 조회, 반환 문서 100 / 300 / 500개, 누락·중복 0. 회차 배열 JSON UTF-8 약 118 / 354 / 591 KB |
| 경합·응답 유실·크기 제한·삭제 | 실제 Emulator, 독립 Firebase Client 두 개 | 메타데이터 CAS 승자 한 명, 동일 재요청에도 문서 업데이트 시각 유지, 크기 초과 쓰기 원자적 실패, 삭제된 회차 부활 차단 |
| 로컬 복구본 재시작 | 실제 Chromium IndexedDB | 브라우저 문서 재로드, UID·작품·회차별 격리, 여러 편집 세션 및 늦은 저장 방지 확인. 저장 공간 초과 오류는 주입으로 검증 |

조회 요청 수와 반환 문서 수를 별도로 기록합니다. 회차 JSON 크기는 UI에 전달된 데이터이며 Firestore wire 크기와 청구량은 별도입니다. 기존 커밋의 동등 벤치마크 및 실제 청구 비용은 미측정입니다. 1,000화 스트레스, 초기 회차 페이지네이션, 대량 가져오기의 장애 재개 및 이전 LocalStorage 복구본 자동 이관도 검증 범위에 포함되지 않았습니다.

새 패키지, Firestore 컬렉션, 인덱스 설정 및 운영 마이그레이션 없이 적용됩니다. 되돌릴 때는 새 브라우저 키에 있는 동기화되지 않은 복구본을 먼저 다운로드하세요. 이후 저장 안정화 커밋을 revert하면 기존 저장 경로로 돌아갑니다. Stage 2.2의 모듈 분리에서는 트랜잭션의 읽기→쓰기 순서, 편집 범위 확인, Draft 순서 검사 및 SSOT 경로를 유지합니다.
